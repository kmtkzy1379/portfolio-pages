Portfolio 01

FEP模倣AItuberアプリケーション

YouTube Liveで視聴者のコメントにリアルタイムで応答するAI配信者アプリ。脳の情報処理を模倣するFEP機構を組み込み、AIの自律的な振る舞いを検証した。

Python Gemini API YouTube API VOICEVOX FEP

1. 目的

AIは急速な進化を遂げていますが、いまだ人間のように低エネルギーで高速・高精度の処理を行うには至っていません。 この課題に対し、私は「人間の脳機能や意識のメカニズムを模倣することで、AIはより効率的かつ高度な応答が可能になる」という仮説を立てました。

本プロジェクトは、この仮説に基づき、脳の情報処理モデルである「自由エネルギー原理（FEP）」を模倣したフィードバック機構をAIに組み込み、自律的な振る舞いがどの程度実現できるかを検証する実験的な試みです。 多様なユーザーとの対話を通じてAIの内部モデルが発達していく過程を観測するため、YouTube Live上で半自動的に配信を行うアプリケーションとして設計しました。

2. システムの動作フロー

本アプリケーションは、以下の流れで動作します：

  1. コメント取得： YouTube LiveのコメントをAPI経由でリアルタイムに取得
  2. FEPフィードバックによる応答生成： 取得したコメントに対し、FEP機構（予測 → 誤差検出 → 内部モデル更新）を通じて応答を生成
  3. 音声合成： 生成した応答テキストを音声に変換
  4. 配信： Live2Dでキャラクターを動かしながら、YouTube Liveで視聴者に配信

3. 結果と課題

  • 精度： FEPフィードバックによる応答精度の明確な向上は実感できなかった
  • 応答速度： フィードバックループの処理負荷により応答が遅く、リアルタイム性に課題が残った
  • 会話の成立： 適切な応答や文脈に沿った記憶の継続は実現できている
  • 長期記憶： 長期記憶の参照時にハルシネーション（事実と異なる記憶の生成）が起きやすい
  • 外部連携： Live2DやVOICEVOXなど各種サービスとの通信は正常に動作

これらの課題を受け、Portfolio 07では以下の改善を行いました：

  • 応答速度 → 思考の階層化（応答AIとフィードバックAIの分離）で高速化
  • 長期記憶のハルシネーション → RAGによるハイブリッド記憶で改善
  • 受動的な応答 → 再帰的メタ認知で自発的発話を実現

Portfolio 05

身体的・神経的制約がAIの歩行学習と進化に与える影響の検証

AIに「体が重い」「反応が遅い」といった身体的ハンデを与えたら、どんな歩き方を学ぶか？強化学習で検証し、「制約が独自の戦略を生む」という知見を得た実験。

Unity ML-Agents Python PPO（強化学習）

目的

Unity ML-Agentsを用いた強化学習実験。生物学的な制約（ハンデ）を与えたAIが、どのような歩行戦略を独自に獲得するかを検証しました。

実験設定：2つの制約モデル

  • Scale Model（体が重い）： 身長1.5倍・質量3.375倍に拡大し、筋力は2.25倍に留めることで、相対的な筋力不足を再現
  • Delayed Model（反応が遅い）： 行動決定の間隔を標準の2倍（20フレーム毎）にし、神経伝達の遅延をシミュレート

検証結果

Normal（水色）、Scale（オレンジ）、Delayed（紫）の3モデルの学習推移:

累積報酬
Delayedモデルは初期に苦戦するが、最終的には最高スコアを記録。

生存時間
Normalが最も安定。Delayedは報酬が高い反面、生存時間は極端に短い。

学習損失
全モデル収束するが、Delayedは変動が激しく、常にギリギリの制御。

考察

  • Scale Model（慎重な保守派）： 「ゆっくり歩くが、転びにくい」戦略を獲得。重心を低く保つ省エネ型のフォーム。
  • Delayed Model（ハイリスク・ハイリターン）： 「転ぶまでの短時間に大股で距離を稼ぐ」極端な戦略を獲得。

「ある機能の制約が、別の機能の過剰な発達や独自の戦略を生む」という、人間のニューロダイバーシティ（神経多様性）にも通じる現象をAIが自律的に再現しました。

使用技術

Unity 6 / ML-Agents 4.0.0 / Python 3.10 / PPO (Proximal Policy Optimization)

LLM Fine-tuning（LoRA）：意識模倣とペルソナ構築の検証

Python LoRA Qwen2.5-14B Unsloth Google Colab

目的

モデルの内部構造（重み）を書き換えることで、特定の性格を持つAIを構築できるかを検証。Qwen2.5-14B-Instructをベースに、Google Colab（T4 GPU）でLoRA（少量データで大規模モデルの一部だけを効率的に学習させる手法）による微調整を実施しました。

失敗と学び

初期実験で直面した問題と、そこから得た知見:

  • 破滅的忘却： 特化データだけで学習すると、元の汎用知識が失われた → 「知識維持データ」と「ペルソナ特化データ」の混合設計が不可欠

低リソース環境での工夫

Portfolio 07

FEP模倣AItuber改良版：マルチモード統合システム「Eve AI」

Portfolio 01の大幅改良版。対話・ゲーム実況・YouTube Liveの3モードで動作する自律型AIキャラクター「Eve」を構築。応答速度・記憶・自発性の3点を重点的に改善した。

Python Groq API GPT-4o VOICEVOX RAG（検索拡張生成） FEP asyncio

Portfolio 01からの3つの改善点

  • 思考の階層化： 応答AI（直感的・高速）とフィードバックAI（熟考的・非同期）に分割し、応答速度を犠牲にせずに品質を向上
  • 自発的な発話： AI自身の応答や「ユーザーが無言」といった状況を再入力し、AI自身を起点とした発話を実現
  • ハイブリッド記憶： RAG（関連する過去の会話を検索して文脈に加える仕組み）による長期記憶と、直近の会話を保持する短期記憶を組み合わせた人間に近い記憶モデル

技術選定の理由

  • Groq API + Llama 3.3 70B： FTモデルよりAPI経由の方が自然な会話が成立。GPT-4系と同等速度で低コスト
  • GPT-4o Vision（OCR）： オープンソースOCRではノベルゲームの装飾文字の認識精度が不足したため採用
  • VOICEVOX： Style-Bert-VITS2はRadeon GPUでCUDA依存エラーが解消できず、安定性と速度を優先

FEP機構（詳細はこちら）

  • 応答AI（直感処理）： ユーザー入力にリアルタイムで応答
  • フィードバックAI（内省処理）： 応答を非同期で評価し、予測誤差を算出して内部モデルを更新

結果と課題

成果： 無言時の自発的発話、RAGによる過去の記憶参照、自然な会話の成立を実現。

課題：

  • 同一入力に同一応答を返す傾向 → ランダム性の注入で改善予定
  • ゲーム実況モードでOCRがボトルネック
  • 応答が丁寧すぎる・感情のない棒読み音声 → FTとの併用、Style-Bert-VITS2での音声学習で改善予定

さらなる発展として、Portfolio 08ではEveに人間のような視覚認識（VLM）を付与し、画面を共有しながら会話できるシステムへと進化させました。

Portfolio 08

Eve AI + VLM：人間のような視覚認識を統合した画面共有AIアシスタント

Eve AIに人間のような視覚認識を付与。9段ステージの画面認識パイプラインにより、画面をEveと共有しながら自然に会話できるシステムへ進化させた。

Python Groq API（Llama 4） OpenAI API YOLOv11 litellm pHash + SSIM MediaPipe VOICEVOX

1. 目的

Portfolio 07で構築したEve AIは、テキストベースの対話においては自然な会話を実現していました。 しかし、よりUXを高めるためには「一緒に作業している」「画面の状況を共有している」という共感・共同体験の要素が不可欠だと感じました。

また、Portfolio 07 ではゲーム実況モードのOCRがボトルネックとなっており、画面の内容を把握する手段がテキスト抽出に限られていました。 そこで本プロジェクトでは、OCRに依存しない9段ステージの画面認識パイプラインを独自設計し、Eveに人間のような視界（Visual Perception）を付与しました。 人間が普段「なんとなく画面全体を眺めつつ、気になった部分だけ注視する」という自然な視覚処理を、AIで再現することに挑戦しています。

2. 仕組み：3層の視覚認識メカニズム

人間の視覚的注意のメカニズム（選択的注意・不随意的注意）を参考に、3層構造の認識システムを実装しました。

裏側では独自設計の9段ステージVLMパイプライン（画面キャプチャ → pHash+SSIM変化検出 → YOLOv11物体検出 → BoT-SORT追跡 → Optical Flow動き分析 → PerID分析 → SceneGraph構築 → DeltaEncoder差分圧縮 → LLMナレーション生成）が5fpsで常時稼働しています。

  • 層1 — パッシブ認識（常時俯瞰）： VLMパイプラインの処理結果がVisionBufferに蓄積され、毎ターンのシステムプロンプトにシーンジャーナルとして注入される。Eveは常に「今画面に何があるか」を浅く把握している状態
  • 層2 — アクティブ認識（意識的注視）： Eve（応答AI）がFunction Callingで画面情報取得・画像解析・監視モード切替を能動的に呼び出し、会話の文脈から「画面を見る必要がある」と判断した場合に詳細な画面認識を実行
  • 自動プッシュ（変化への反応）： pHash + SSIMの2段階変化検出でMAJOR（ウィンドウ切り替えレベル）/ MODERATE / MINORを分類。MAJOR変化は自動的に会話に割り込んで声をかける。監視モード有効時はMODERATE変化にも反応。重複検出やプログレッシブクールダウン（15s→30s→60s）で過剰反応を抑制

3. 試行錯誤

VLM機能の実装にあたっては、以下のような技術的課題と向き合いました：

  • 画面を見る意思とタイミングの問題： 応答AIが自発的に「画面を見よう」とする意思を持たせることが困難だった。画面の内容について質問しても「分からない」の一点張りになったり、見てもいないのに見えたかのようなハルシネーション（幻覚応答）を起こす問題が発生。最終的にFunction Callingによる能動的な画面参照と、監視モードの切替機構で解決した
  • 反応の閾値調整： 常時画面認識を送り続けると、些細な変化にもいちいち反応して煩わしくなるか、逆に全く反応しなくなるかの二極化が起きた。pHash+SSIMの2段階変化検出、ナレーション重複検出（SequenceMatcher）、プログレッシブクールダウン、ベースライン比較などの仕組みを組み合わせて解決。Live2Dキャラのアイドルアニメーション（揺れ・瞬き）の誤検出もナレーション重複検出とYOLOのclass_whitelist調整で抑制した
  • 人力による感性ベースの検証： この閾値調整は「人がどう感じるか」という感性の問題であるため、AIによる自動検証が不可能だった。細かくパラメータを変更しながら人力で繰り返し検証し、ハルシネーション・無反応・過剰反応の全てを防ぐバランスを探り当てた

4. 成果

これらの試行錯誤の結果、ユーザーの画面をEveと共有しながら自然に会話できるアプリケーションへと進化しました。 Eveはウィンドウの変化に気づいて声をかけたり、画面に映っている内容について的確にコメントしたりと、まるで隣で一緒に画面を見ている人間のような振る舞いを実現しています。

5. 技術的アピールポイント

  • 9段ステージの画面認識パイプラインを独自設計： キャプチャ → 変化検出 → 物体検出 → 追跡 → 動き分析 → 個別分析 → シーングラフ → 差分圧縮 → ナレーション生成の一連を3スレッドで並列処理
  • CV技術とLLMの統合： YOLOv11、BoT-SORT、MediaPipe、DeepFace、Optical Flowといったコンピュータビジョン技術と、Llama 4 Scout/Maverickによる言語理解を一つのシステムに統合
  • Eve (asyncio) × VLM (threading) のブリッジ設計： 非同期ベースのEveとスレッドベースのVLMパイプラインを VLMBridge で橋渡しし、リアルタイム性を維持
  • 認知科学の応用： 人間の選択的注意・不随意的注意のメカニズムをAIの画面認識に応用した独自の設計アプローチ
  • UX駆動の開発： 単なる技術的な正しさではなく、「人の感性に合う反応の閾値」を人力で探索するUX重視の開発プロセス

PromptLore：CLAUDE.md / skills 共有SNS

非エンジニアでも簡単に Claude Code の CLAUDE.md・skills をアップロード／ダウンロードできる共有SNS。ファイル選択だけで種別自動判定、コピペで即使用できる設計で、フォークやブランチ管理といった技術的ハードルを排除した。

Ruby on Rails 8.1 Ruby 3.4 Devise SQLite Hotwire (Turbo / Stimulus) ActiveStorage Redcarpet Pagy Kamal Docker Fly.io

1. 目的

X や Qiita を観察すると、現在 Claude Code は多種多様な人々に使用されていると感じました。その中には非エンジニアも存在しており、Claude Code を使用しているが CLAUDE.md や skills を十分に活用できていない方もいます。 一方、GitHub での CLAUDE.md / skills の管理は fork やブランチ運用が必要で、非エンジニアにとってはまだまだハードルが高いのが現状です。

また、エンジニアであっても時間が足りず、「どの CLAUDE.md / skills を使えばよいか分からない」という選択コストを抱える方が多いと推測できます。 そこで、CLAUDE.md と skills を手軽にアップロード／ダウンロードできる SNS 基盤として PromptLore を制作しました。

2. 主要機能

  • アップロード： ファイルを選択するだけで CLAUDE.md か skills かを自動判別してアップロード。バージョン履歴を最大 5 件まで保存し、Public / Private を切替可能。
  • ダウンロード： 非エンジニアでもファイル配置しやすいよう、コピペするだけで使用できる設計。コピペ後の行動指示も明記。CLI が使えないケースも考慮し、WEB版 Claude Code とローカル版 Claude Code の両方に対応。
  • プリセット機能： CLAUDE.md と skills の抱き合わせリポジトリをまとめてアップロード／ダウンロードできる。これにより、組み合わせを考えずに即座に使用可能。
  • 高評価機能： ユーザーのモチベーション向上と信頼性の獲得を目的としたアクション。
  • Official機能： 私が一つ一つ確認し、信頼できると判断したリポジトリに Official フラグを付与。利用者に安心感を提供する。
  • 検索機能： キーワード検索・タグ検索・カテゴリ検索で、自身が取り組みたい開発にマッチした CLAUDE.md と skills を高速に探せる。
  • アカウント管理： Devise によるメールアドレス＋パスワード認証。ユーザー名・アイコンの設定が可能。

3. 技術選定の理由

  • Ruby on Rails 8.1： ActiveStorage（ファイル添付）、Turbo / Stimulus（SPA 的な UX）、Solid Queue（非同期処理）が標準で揃い、Web アプリ初制作でも生産性高く全機能を実装できた。
  • SQLite + Solid Cache / Queue / Cable： Rails 8 の "Solid Trifecta" 構成。初期運用に十分なパフォーマンスとシンプルな構成を両立。
  • Devise： 認証機能を短時間で堅牢に実装するためのデファクト。
  • Redcarpet + Rouge： CLAUDE.md の中身を Web 上で Markdown プレビュー・シンタックスハイライト表示し、ダウンロード前に内容を確認できるようにした。
  • Kamal + Docker + Fly.io： コンテナベースで低コストに本番公開。CI/CD の敷居を下げつつ、個人開発でも本格的な運用を実現。

4. 今後の課題

  • 豊富な CLAUDE.md / skills のシード投入（キラーコンテンツの用意）
  • CSS のリファクタによるデザイン性の向上
  • API 連携による完全自動配布： コピペ作業を無くし、Claude Code 側と直接連携して自動で CLAUDE.md / skills を反映する仕組み
  • 細かな動作テストの整備
  • ユーザー獲得（コミュニティ形成）

PromptGolf：ことばでキャラを動かすローカルLLMパズルゲーム

「3マス進んで、右を向いてジャンプ」——日本語で書いた指示をPC内のローカルAI（LLM）が解釈し、キャラクターをゴールへ導くパズルゲーム。スコアは「トークン数＋指示回数」で決まり、少ない・的確なことばでクリアするほど高得点。遊びながらプロンプトの書き方が身につく。itch.io にて無料公開中。

Unity 2022.3 C# llama.cpp Qwen3.5-9B（ローカルLLM） JSON Schema 構造化出力 UniVRM itch.io（Butler）

1. 目的

プロフィールの展望に掲げた「GameとAIの融合」を、初めて一般公開の作品として形にしたプロジェクトです。 「AIに思い通り動いてもらうコツ＝プロンプトの書き方」は今後誰にとっても必要なスキルになると考え、 遊ぶだけでプロンプトエンジニアリングが自然と身につくゲームとして設計しました。

名前の由来はプログラマの遊び「コードゴルフ」（できるだけ短いコードで課題を解く競技）。 本作はできるだけ少ないことばでゴールを目指す「ことばのゴルフ」です。

2. ゲームデザイン

  • 日本語の指示でキャラを操作： 入力した指示文をローカルLLMが解釈し、行動列（歩く・曲がる・ジャンプ・しゃがみ等）に変換して実行
  • スコアリング： 「使ったトークン数＋指示回数」が少ないほど★3に近づく。曖昧な指示はAIが誤解する——的確に伝える力がそのまま攻略になる
  • ギミック： 段差・しゃがみ通路・ボタンと扉・鍵・一方通行などを組み合わせたステージ構成
  • 学習モード＋クイズ： トークン・コンテキスト・ハルシネーションといったAIの仕組みから「上手な指示のコツ」までを体系的に学べる
  • VRMアバター対応： 手持ちの .vrm を読み込めば好きなキャラでプレイ可能（モーション確認用のVRMスタジオも搭載）
  • ステージビルダー： ギミックを自由に配置して自作コースを作成
  • AI自由会話： 遊び方の質問にもゲーム内AIが回答

3. 技術的アピールポイント

  • ローカルLLMをゲームに同梱： 推論エンジン llama.cpp（llama-server）と Qwen3.5-9B（GGUF 4bit量子化）を組み込み、APIキー不要・通信なし・完全ローカル動作を実現。入力はプレイヤーのPCの外に出ない
  • 5.6GBモデルの配布問題を解決： itch.io の容量制限のためモデルは同梱せず、初回起動時に Hugging Face から自動ダウンロード＋SHA256による整合性検証。保存先を永続領域に分離し、ゲーム更新時の再ダウンロードも回避
  • JSON Schema による構造化出力： LLMの出力を json_schema 制約付きデコーディングで行動列JSONに強制し、ハルシネーションによる不正な行動を構造レベルで防止
  • LLMプロバイダの抽象化： ILlmProvider インターフェースでローカル／リモートを差し替え可能な設計
  • UniVRM ランタイムロード： ユーザーの .vrm を実行時に読み込み、揺れ物（スプリングボーン）やモーションの動作確認までゲーム内で完結

本作は、プロフィールに記載したAI協調開発フローを全面的に実践した初の作品です。 AIコーディングエージェント（Claude Code）に Unity エディタの自動操作（Unity MCP・C#エディタ拡張）まで任せて実装を推進し、 私は企画・仕様策定・設計判断・ビジュアル/UXの検証・最終品質判断を担当しました。 設計の分岐点では複数のAIエージェントに根拠付きで議論させて意思決定するなど、「AIを的確に制御して完遂させる」開発スタイルを検証しています。

自由エネルギー原理（FEP）とは？

ポートフォリオ①・⑦・⑧で活用している理論の、簡易説明です。

自由エネルギー原理（Free Energy Principle）は、神経科学者カール・フリストンが提唱した、脳の働きを説明する理論です。

簡単に言うと、「脳は常に"次に何が起こるか"を予測していて、予測が外れたとき（＝驚いたとき）に、その"驚き"をなるべく小さくしようとする」という考え方です。

たとえば、コーヒーだと思って飲んだらお茶だった場合、脳は「予測と違う！」と驚きます。このとき脳は2つの方法で驚きを減らそうとします：

  • 考えを変える（知覚の修正）： 「あ、これはお茶だったんだ」と自分の認識を更新する
  • 行動する（能動的推論）： 次からはコップの色を確認してから飲む、という行動で予測の精度を上げる

本ポートフォリオのAIシステムでは、この「予測 → 誤差の検出 → 修正」というループをプログラムで再現しています。 AIが自分の応答を振り返り（メタ認知）、「もっとこう答えるべきだった」と内部モデルを更新し続けることで、単なる命令応答型ではない、自律的な振る舞いを目指しています。
